JPA 공부를 시작하면 `@Entity`, `persist`, 영속성 컨텍스트 같은 용어가 한꺼번에 쏟아집니다. 저는 문법부터 외우다가 "그래서 이게 왜 필요한데?"에서 막혔고, 결국 **JDBC로 직접 짜 보면 어디가 불편한지**부터 정리하니 이해가 빨랐습니다.

예제는 **도서관 대출 서비스**(책, 출판사, 이용자, 대출)로 통일했습니다. 환경은 Java 17, Spring Boot 3(Hibernate 6), MySQL 8입니다.

> 참고한 자료: 인프런 김영한님의 JPA 기본편 강의, Jakarta Persistence 명세, Hibernate ORM 공식 문서

## 1. 출발점: 책과 출판사를 JDBC로 저장해 보기

도서관 서비스에서 `Book`은 하나의 `Publisher`에 속합니다.

```java
public class Publisher {
private Long id;
private String name;
}

public class Book {
private Long id;
private String title;
private Publisher publisher; // 객체라면 이렇게 참조로 갖고 싶다
}
```

이걸 JDBC로 저장하려면 이렇게 됩니다.

```java
public void save(Book book) throws SQLException {
String sql = "INSERT INTO book (title, publisher_id) VALUES (?, ?)";
try (Connection con = dataSource.getConnection();
PreparedStatement ps = con.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {
ps.setString(1, book.getTitle());
ps.setLong(2, book.getPublisher().getId()); // 객체를 FK 값으로 풀어서 넣기
ps.executeUpdate();
try (ResultSet rs = ps.getGeneratedKeys()) {
if (rs.next()) book.setId(rs.getLong(1));
}
}
}
```

조회는 더 길어집니다. 조인한 결과에서 책 컬럼과 출판사 컬럼을 하나씩 꺼내 `Book`과 `Publisher`를 직접 조립하고 `setPublisher`로 이어 붙여야 합니다.

여기서 불편함이 두 종류로 보입니다.

### 1 반복 노동

- 테이블마다 INSERT/SELECT/UPDATE/DELETE를 쓰고, ResultSet을 객체로 옮기는 코드도 쓴다.
- `Book`에 `isbn` 필드 하나를 추가하면 위 SQL과 매핑 코드를 **전부** 찾아 고쳐야 한다. 하나라도 놓치면 런타임에 터진다.

### 2 객체 설계가 SQL에 끌려간다

- DAO가 어떤 SQL로 조회했느냐에 따라 `book.getPublisher()`가 채워져 있을 수도, `null`일 수도 있다.
- 그래서 서비스 코드에서 `book.getPublisher().getName()`을 부를 때마다 "이거 조인해서 가져온 건가?"를 확인하게 된다.
- 결국 `findBook()`, `findBookWithPublisher()`, `findBookWithPublisherAndLoans()` 같은 메서드가 늘어난다.

즉 **엔티티를 신뢰하고 쓸 수 없는** 상태가 됩니다.

## 2. 근본 원인: 객체와 관계형 DB는 모델이 다르다

이 불편함은 코드를 잘못 짜서가 아니라 두 세계의 모델이 달라서 생깁니다. 이를 흔히 **객체-관계 임피던스 불일치**라고 부릅니다.

| 주제 | 객체 세계 | 관계형 DB 세계 |
|---|---|---|
| 연결 방식 | 참조 (`book.getPublisher()`) | 외래 키 + 조인 |
| 상속 | 있음 (`Book extends Media`) | 없음 (비슷하게 흉내만 냄) |
| 동일성 | 참조 비교(`==`)와 `equals()` | 기본 키(PK) 값 |
| 탐색 | 점(`.`)으로 자유롭게 | 조인으로 미리 가져온 범위만 |

### 연관관계: 참조 vs 외래 키

객체는 방향이 있습니다. `Book`이 `Publisher`를 참조하고 있어도, `Publisher`에서 `Book`을 찾으려면 참조를 따로 만들어야 합니다. 반면 테이블은 `book.publisher_id` 하나로 양쪽 조회가 모두 됩니다. 그래서 객체를 DB에 맞춰 **FK 값만 필드로 들고 있는 모델**로 만들면 DB와는 편하지만 객체 협력이 어려워집니다.

```java
// 테이블 중심 모델 - 객체답지 않다
class Book { Long publisherId; }
// 쓸 때마다 다시 조회해야 한다
Publisher p = publisherDao.find(book.getPublisherId());
```

### 상속

`Media`를 부모로 `Book`, `Dvd`가 있다고 해 봅시다. 저장하려면 부모 테이블과 자식 테이블 INSERT를 둘 다 쓰고, 조회하면 조인과 타입 판별을 직접 해야 합니다. 이 번거로움 때문에 DB와 엮이는 객체에는 상속을 일부러 안 쓰게 됩니다. 반면 `List<Media>`에 넣고 꺼내는 건 한 줄입니다.

### 동일성

```java
Book a = bookDao.find(1L);
Book b = bookDao.find(1L);
System.out.println(a == b); // false: 호출마다 new 로 만드니까
```

컬렉션에서 꺼냈다면 같은 인스턴스일 텐데, DB에서 꺼내면 다릅니다. 같은 행인데 객체는 둘이라 한쪽만 수정하는 사고가 납니다.

## 3. ORM이라는 해법

결국 개발자가 하던 "객체와 SQL 사이의 변환"을 **프레임워크가 대신하게** 하자는 것이 ORM(Object-Relational Mapping)입니다.

- 객체는 객체답게, 테이블은 테이블답게 설계한다.
- 둘 사이의 매핑 규칙만 선언한다. (어노테이션 또는 XML)
- SQL 생성과 결과 조립은 ORM이 한다.

### JPA, Hibernate, Spring Data JPA는 뭐가 다른가

자주 헷갈려서 한 번 정리해 둡니다.

| 계층 | 역할 |
|---|---|
| Spring Data JPA | 리포지토리 편의 기능. 인터페이스만 만들면 CRUD를 제공하며, 내부에서 JPA를 사용한다 |
| JPA (Jakarta Persistence) | 표준 인터페이스와 명세 |
| Hibernate | JPA를 실제로 구현한 구현체 (EclipseLink 등도 있음) |
| JDBC | 마지막에 DB와 통신하는 자바 표준 API |

위에 있는 것이 아래에 있는 것을 사용하는 구조입니다.

- **JPA**는 "이렇게 쓰자"는 표준(인터페이스)입니다.
- **Hibernate**는 그 표준을 실제로 구현한 라이브러리이고, 사실상 표준처럼 쓰입니다.
- **Spring Data JPA**는 JPA 위에 얹은 편의 계층입니다. 이 글에서는 그 밑바닥의 JPA를 기준으로 설명합니다.

참고로 JPA는 과거 `javax.persistence`였지만 Jakarta EE로 넘어오면서 `jakarta.persistence`가 되었습니다. Hibernate 6 이상, Spring Boot 3 이상은 `jakarta`를 씁니다.

## 4. JPA를 쓰면 코드가 어떻게 달라지나

아까 JDBC로 쓴 저장·조회가 이렇게 줄어듭니다.

```java
em.persist(book); // 저장 (INSERT는 JPA가 생성)
Book found = em.find(Book.class, 1L); // 조회 (SELECT도 JPA가 생성)
found.setTitle("개정판"); // 수정 - UPDATE를 직접 호출하지 않는다
em.remove(found); // 삭제
```

필드 추가도 엔티티에 필드만 더하면 INSERT/SELECT/UPDATE가 바뀐 모양으로 만들어집니다.

연관관계도 객체 방식 그대로입니다.

```java
book.setPublisher(publisher);
em.persist(book); // publisher_id 는 JPA가 채움

Book found = em.find(Book.class, 1L);
String name = found.getPublisher().getName(); // 그냥 점으로 탐색
```

점으로 탐색할 때 필요한 데이터를 **그 시점에** 가져오는 것이 지연 로딩이고, 그래서 "처음에 어떤 SQL로 조회했는가"에 덜 얽매입니다. 같은 영속성 컨텍스트 안에서는 같은 PK를 조회하면 같은 인스턴스를 돌려주므로 앞서 본 `a == b` 문제도 사라집니다. 이 동작은 같은 트랜잭션에서 불러온 엔티티를 JPA가 한 곳(**영속성 컨텍스트**)에서 관리하기 때문에 가능합니다.

## 5. 성능 측면의 장점도 있다

- **같은 요청 안의 중복 조회 제거**: 같은 PK를 두 번 `find` 하면 두 번째는 SQL이 나가지 않습니다.
- **쓰기 모아서 보내기**: INSERT/UPDATE/DELETE를 커밋 직전에 모아 한 번에 보낼 수 있어, JDBC 배치를 켜면 왕복을 줄일 수 있습니다.
- **필요할 때 가져오기**: 지연 로딩으로 안 쓰는 연관 데이터는 조회하지 않습니다.

## 6. 단점과 주의점

장점만 있었다면 모두가 쓰겠죠. 저는 아래 정도를 염두에 두고 있습니다.

- **학습 비용**이 크다. 편한 대신 내부 동작(영속성 컨텍스트, 프록시)을 모르면 이해 안 되는 SQL이 나간다.
- **복잡한 통계·리포트 쿼리**는 JPQL로 표현하기 어렵다. 이럴 땐 QueryDSL이나 네이티브 SQL을 섞어 쓴다.
- ORM이라고 DB 지식이 필요 없어지는 게 아니다. 객체 설계와 테이블 설계를 **둘 다** 이해해야 한다. 로그에 찍힌 SQL을 읽을 줄 알아야 한다.
- 잘못 쓰면 N+1 같은 성능 문제를 쉽게 만든다.

그래서 저는 JPA를 쓸 때 항상 **SQL 로그를 켜 놓고** 어떤 쿼리가 나가는지 확인합니다.
