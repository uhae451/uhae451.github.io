> 금융 지수 대시보드 서비스 Findex를 4명이 약 1주 동안 개발하고, **D파트(대시보드 + 운영)** 를 맡아 정리한 개발 리포트입니다.

## 1. 프로젝트 개요

Findex는 금융위원회 Open API에서 주가 지수 정보와 일별 시세를 가져와 저장하고, **차트·성과·랭킹**으로 보여 주는 금융 지수 대시보드 서비스입니다.

| 파트 | 내용 |
|---|---|
| A | 공통 모듈 + 지수 정보 |
| B | 지수 데이터 |
| C | 외부 연동 + 배치 |
| **D (나)** | **대시보드 + 운영** |

핵심 기능은 다음과 같습니다.
- 지수 정보·데이터 관리
- 외부 API 연동
- 대시보드(차트, 성과, 랭킹)
- 연동 작업 이력 조회

## 3. 기술적 성과

### 기술 스택
Java 17, Spring Boot 4.1.1, Spring Data JPA, QueryDSL, MapStruct, PostgreSQL, JUnit5 · Mockito · AssertJ, Railway

### 주요 구현
- **계산기 분리**: 등락률(`FluctuationCalculator`)과 이동평균(`MovingAverageCalculator`)을 `@Component`로 분리해 차트·성과·랭킹이 같은 계산기를 재사용합니다.
- **성과 기준일 설계**: 오늘이 아니라 **그 지수의 가장 최신 데이터 날짜**를 기준으로, 일간 1일·주간 7일·월간 한 달 전 종가와 비교합니다. 비교 데이터가 없는 지수는 결과에서 제외합니다.
- **랭킹**: 등락률 내림차순, 동률은 id 오름차순이고 limit은 기본 10(1~100 범위 밖이면 10)입니다.
- **QueryDSL 동적 쿼리**: `QueryRepository` + `Impl` 구조로 필터 5개를 조합하고, null 조건은 무시되는 `BooleanExpression`을 사용했습니다.
- **커서 페이지네이션**: 팀 공통 `CursorPaging`을 사용하고, 연동 작업 목록은 대상 날짜 null을 1970-01-01로 바꿔 DB와 상관없이 같은 순서를 보장했습니다.
- **TDD**: 계산기 → Repository(`@DataJpaTest`) → Service(Mockito) → Controller(`@WebMvcTest`) 순서로 쌓았습니다.

## 4. 문제점 및 해결 과정 (STAR)

### ① 팀원의 DB 구조 변경으로 내 테스트가 전부 깨짐

- **상황 (Situation)**: `develop` 브랜치를 받아 합친 뒤, 직전까지 통과하던 Repository 테스트가 전부 실패했습니다.
- **과제 (Task)**: 내 코드의 문제인지 다른 파트 변경의 영향인지 가려내고, 테스트를 복구해야 했습니다.
- **행동 (Action)**:
 1. 실패 로그와 새로 합쳐진 변경 내용을 비교했습니다.
 2. B가 `index_data`에 지수 정보 외래 키를 추가했고, 지수 없이 시세만 저장하던 내 테스트가 거절된다는 것을 확인했습니다.
 3. `setUp`에서 지수 정보를 먼저 저장하도록 바꾸고, 하드코딩해 둔 id를 실제로 저장된 id로 교체했습니다.
- **결과 (Result)**: 테스트가 다시 통과했습니다. 이후 머지할 때마다 전체 테스트를 바로 돌려 다른 파트의 변경이 미치는 영향을 확인하는 습관이 생겼습니다.

### ② 전체 실행에서만 실패하는 테스트

- **상황 (Situation)**: 연동 이력 Repository 테스트가 단독 실행은 통과하는데, 전체 테스트를 돌리면 5개가 실패했습니다.
- **과제 (Task)**: 테스트가 실행 순서나 다른 테스트의 데이터에 영향을 받지 않도록 격리해야 했습니다.
- **행동 (Action)**:
 1. 단독 실행과 전체 실행의 결과를 비교해, 다른 테스트가 `SyncJob` 데이터를 남겨 "내가 넣은 3건만 있다"는 가정이 깨진다는 것을 파악했습니다.
 2. 각 테스트 시작 시 `SyncJob` 테이블을 비우는 `cleanUp`을 추가했습니다. 테스트 트랜잭션 안에서 실행되므로 종료 시 롤백되어 실제 데이터에는 영향이 없습니다.
 3. 원인이 된 다른 테스트의 데이터 정리는 팀에 공유할 사항으로 정리했습니다.

```java
@BeforeEach
void cleanUp() {
 entityManager.createQuery("delete from SyncJob").executeUpdate();
}
```

- **결과 (Result)**: 전체 실행에서도 안정적으로 통과했습니다. 공유 DB를 쓰는 테스트는 자기가 넣은 데이터만 보도록 격리해야 한다는 것을 배웠습니다.

### ③ Railway 배포 5번의 연속 실패

- **상황 (Situation)**: 기능 구현을 마치고 처음으로 Railway에 배포했는데, 빌드·시작·DB 연결 단계에서 다섯 번 연속으로 실패했습니다.
- **과제 (Task)**: 마감 전에 서비스가 정상 기동하도록, 실패할 때마다 배포 로그에서 원인을 찾아 해결해야 했습니다.
- **행동 (Action)**: 실패할 때마다 배포 로그를 읽고 원인을 하나씩 좁혀 해결했습니다.

| 단계 | 증상 | 한 일 |
|---|---|---|
| ① 빌드 | Java 17 설치를 찾을 수 없음 | 빌더 기본값이 Java 21인 것을 확인하고 `railpack.json`에 Java 17을 지정 |
| ② 시작 | 시작 명령이 1초마다 실패 | 기본 명령이 하위 모듈 경로를 가정하는 것을 확인하고 시작 명령을 직접 고정 |
| ③ 설정 미적용 | 파일을 올려도 같은 로그 | `main` 브랜치를 배포 중이고 GitHub에 Railway 앱이 미설치인 것을 찾아, 앱을 설치하고 배포 브랜치를 변경 |
| ④ DB 주소 | 주소가 `jdbc:postgresql://:/` | 참조 변수가 빈 값인 것을 확인하고 DB 주소와 사용자명을 값으로 직접 입력 |
| ⑤ DB 인증 | `user "root"`로 접속 시도 | 비밀번호·사용자명이 비어 OS 사용자로 접속한 것을 확인하고 값을 채워 재배포 |

- **결과 (Result)**: 서비스가 정상 기동했습니다. 변수를 고친 뒤에도 같은 오류가 반복된 이유가 **새 배포가 실패하는 동안 예전 서버가 계속 응답하기 때문**이라는 것을 알게 되었고, 이후에는 배포가 Online이 된 것을 확인한 뒤에 호출했습니다.

### ④ 기간 계산 미구현으로 인한 Mockito 오류

- **상황 (Situation)**: 성과 계산 Service 테스트에서 `PotentialStubbingProblem`이 발생했습니다.
- **과제 (Task)**: 오류의 원인을 찾아 테스트와 구현을 맞춰야 했습니다.
- **행동 (Action)**:
 1. 예외 메시지에서 stub으로 지정한 인자와 실제 호출된 인자가 다르다는 것을 확인했습니다.
 2. 기간별 비교 기준일(`baseDate`)을 구하는 부분이 구현되기 전이라 `startDate`가 null로 넘어간 것이 원인임을 찾았습니다.
 3. `PeriodType`에서 일간 1일, 주간 1주, 월간 한 달 전을 계산하도록 구현하고 `PeriodTypeTest`로 확인했습니다.
- **결과 (Result)**: 테스트가 통과했습니다. Mockito의 엄격한 stub이 구현 누락이라는 잘못된 가정을 먼저 알려 준다는 점을 확인했고, 테스트를 먼저 쓰는 TDD의 장점을 체감했습니다.

## 5. 협업 및 피드백

- **공통 모듈 활용**: A의 `CursorPaging`, `CursorPageResponseDto`, 공통 예외를 그대로 사용해 4개 목록의 구조를 통일했습니다.
- **다른 파트의 변경에 대응**: B의 외래 키 추가, C의 테스트가 남긴 데이터가 제 테스트에 영향을 줬습니다. 문제를 찾아 전달하고 제 쪽을 먼저 안정화했습니다.
- **프런트와의 약속**: 프런트가 차트 응답을 최신순으로 가정해 `reverse()`하고, 성공 이력이 0건일 때 `content[0]`을 읽어 오류가 나는 부분을 코드를 읽어 확인했습니다. 응답 순서를 바꿔 보았지만 1년 치 차트에서 가로 스크롤 UX 문제가 생겨 되돌리고 팀과 협의할 사항으로 남겼습니다.
- **PR 운영**: 기능 단위로 작게 나눠 올려 충돌이 거의 없었습니다. fork + upstream 환경에서 `develop` 동기화를 반복하며 Git 흐름을 익혔습니다.

## 6. 코드 품질 및 최적화

### 가독성과 유지보수성
- 계산 로직을 Component로 분리해 단독 테스트가 가능하고 API 간 재사용이 됩니다.
- 쿼리는 `QueryRepository`와 `Impl`로 분리하고, 동적 조건은 null을 무시하는 `BooleanExpression`으로 조합했습니다.
- 공통 `CursorPaging`으로 정렬과 커서 조건을 한 곳에서 관리해 목록마다 같은 규칙을 씁니다.
- 한글 주석으로 계산 기준과 규칙(기준일, 제외 조건)을 코드에 남겼습니다.
- 테스트 64개로 동작을 고정했고, 테스트 격리(`cleanUp`)로 실행 순서에 영향을 받지 않게 했습니다.

### 성능 관련
- 커서 방식으로 OFFSET 없이 다음 페이지를 조회하고, `size + 1`건만 조회해 다음 페이지 여부를 판단합니다.
- 랭킹의 limit을 1~100으로 제한해 과도한 조회를 막았습니다.
- 아직 개선하지 못한 부분(랭킹 N+1)은 아래 7번에 정리했습니다.

## 7. 향후 개선 사항 및 제안

### D파트 코드
1. 랭킹이 지수별로 쿼리를 반복하는 **N+1**을 한 번의 쿼리나 배치 조회로 개선
2. 종가가 null인 데이터 방어
3. 20일 이동평균이 차트 앞부분에서 비는 문제를 앞선 기간까지 조회해 보강
4. 연동 작업 목록의 `baseDateFrom/To` 필터 지원
5. 시드 데이터 자동화로 시연 환경 준비 단순화

### 프로젝트 팀 차원
6. 테스트용 DB(H2 또는 별도 DB)를 개발 DB와 분리해 시작 시점에 합의
7. 머지 후 전체 테스트를 CI로 자동 실행
8. 공통 의존(엔티티, 예외, 페이지 응답)을 초반에 먼저 머지
9. 첫날 빈 앱이라도 배포해 환경 문제를 미리 발견
10. 프런트와 API 계약(응답 순서, 빈 목록 처리)을 초반에 문서로 확정
11. 개발 중 노출된 API 키 재발급과 DB 비밀번호 교체, 비밀 정보는 저장소에 두지 않는 규칙 유지
