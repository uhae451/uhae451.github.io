로컬에서 실행하던 Spring Boot 프로젝트를 AWS로 옮기고, GitHub Actions로 자동 배포하기까지의 과정을 정리했습니다.

**진행 순서:** 계정 설정 → S3 파일 저장 → RDS 연결 → ECR 이미지 업로드 → ECS 배포 → CI/CD

## 시작하기 전에

이 글은 로컬에서 실행하던 Spring Boot 프로젝트를 AWS로 옮기는 과정입니다. AWS가 처음이더라도 따라갈 수 있도록 순서대로 정리했지만, Spring Boot 프로젝트 실행과 Docker의 기본 사용은 알고 있다는 전제로 진행합니다.

먼저 아래 항목을 준비해줍니다.

- 로컬에서 정상 실행되는 Spring Boot 프로젝트: 아래 코드는 Spring Web, JPA, PostgreSQL 드라이버, Lombok이 설정된 프로젝트 기준입니다.
- 프로젝트에 맞는 JDK와 Gradle Wrapper(`gradlew`)
- Docker와 Docker Compose: Docker를 설치한 뒤 실행까지 해둡니다.
- AWS 계정과 AWS CLI v2: [공식 설치 문서](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html)를 참고해 설치합니다.
- GitHub 리포지토리와 Postman

터미널에서 아래 명령어가 실행되는지 먼저 확인합니다. 이후 터미널 명령은 별도 설명이 없다면 프로젝트 최상위 폴더에서 실행합니다.

```bash
java -version
docker --version
docker info
docker compose version
aws --version
```

이번 실습은 서울 리전(`ap-northeast-2`)을 기준으로 합니다. S3, RDS, ECR, ECS를 생성할 때 같은 리전인지 확인해줍니다. IAM은 리전별로 만드는 서비스가 아니므로 리전 선택이 없는 것이 정상입니다.

프로젝트마다 이름이 다르다 보니 중간에 헷갈릴 수 있습니다. 아래 이름은 설명을 위한 예시이고, 캡처에 보이는 이름보다 **본인이 실제로 생성한 이름**을 기준으로 입력하시면 됩니다.

| 항목 | 예시 또는 확인할 값 |
| --- | --- |
| S3 버킷 | 본인이 생성한 버킷 이름 |
| RDS 초기 데이터베이스 | `db_project` — DB 인스턴스 식별자와 구분 |
| ECR 리포지토리 | `aws-study` |
| ECS 클러스터 | `aws-study-cluster` |
| ECS 태스크 정의 패밀리 | `aws-study-task` |
| ECS 서비스 | `aws-study-service` |
| 태스크 안의 컨테이너 이름 | `aws-study-app` |

RDS와 Fargate 등을 실행하는 유료 실습입니다. 마지막에 실습 리소스를 정리하는 과정까지 함께 확인해줍니다.

## 1. AWS 계정과 기본 설정

### MFA와 IAM 사용자 생성

AWS 유료 계정으로 로그인하면 콘솔 홈으로 이동합니다.
가장 먼저 계정을 보호하기 위해 MFA를 설정합니다. 저는 인증 앱의 OTP를 사용했습니다.

루트 계정에서는 우측 상단 계정 메뉴의 **보안 자격 증명 > MFA 디바이스 할당**으로 들어갑니다. 인증 앱을 선택하여 앱으로 QR 코드를 등록하고, 안내에 따라 연속된 두 인증 코드를 입력합니다. 아래에서 만들 IAM 사용자는 **IAM > 사용자 > 해당 사용자 > 보안 자격 증명**에서 설정할 수 있습니다. [인증 앱 MFA 설정 안내](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_mfa_enable_virtual.html)도 참고하시면 됩니다.

다음은 루트 계정으로 계속 작업하지 않기 위해 IAM에 앞으로 사용할 사용자를 등록합니다. IAM은 AWS의 출입 관리 시스템으로 인증과 인가를 담당하며, 사용자, 그룹, 역할, 정책으로 구성되어 있습니다.

먼저 **IAM > 사용자 > 사용자 생성**으로 들어갑니다. 이번에 만드는 사용자는 콘솔에서 AWS를 관리할 사용자이므로 **AWS Management Console에 대한 사용자 액세스 권한 제공**을 활성화합니다.

이번 실습에서는 권한 설정의 **직접 정책 연결**에서 `AdministratorAccess`와 `IAMUserChangePassword`를 연결합니다. `AdministratorAccess`는 관리자 권한이므로 뒤에서 만드는 애플리케이션용 사용자에게 그대로 연결하지 않습니다.

## 2. S3 버킷 생성과 파일 확인

다음으로는 S3를 사용하여 AWS에 파일을 저장하는 작업입니다. 로컬 디스크에만 파일을 저장하면 디스크에 문제가 생겼을 때 복구가 어려울 수 있으므로, 파일 보관을 AWS에 맡기는 방식입니다.

S3의 구조는 버킷, 객체, 키로 구성되어 있습니다. 버킷은 파일을 담을 그릇, 객체는 저장된 파일, 키는 버킷 안에서 파일을 구분하는 이름이라고 생각하시면 됩니다.

예를 들어 `covers/2026/11/image.png`라는 이름으로 파일을 저장했다면, 폴더처럼 보이는 경로 전체가 객체의 키입니다.

S3에 들어온 뒤 버킷 만들기로 새 버킷을 만듭니다.
이때 서울 리전인지 다시 확인한 뒤, 다른 리전이라면 콘솔 우측 상단의 리전 선택 메뉴에서 변경합니다.

버킷을 만들 때는 이름을 넣고, **모든 퍼블릭 액세스 차단**을 유지한 상태로 생성합니다. 이름이 이미 사용 중이라는 메시지가 나오면 본인만의 접미사를 붙여 다른 이름으로 만들어줍니다.

이때 객체 URL은 존재하지만 해당 URL로 들어가면 access denied가 됩니다.

버킷을 비공개로 생성하여 익명 접근이 허용되지 않기 때문입니다. 이때 객체 작업에서 '미리 서명된 URL과 공유'를

## 3. Spring Boot와 S3 연동

### S3 접근 정책과 액세스 키 생성

앞에서는 콘솔에서 직접 이미지를 업로드했습니다. 이제 기존에 로컬에서만 파일을 저장하던 프로젝트에서 S3에 이미지를 저장하고 불러오도록 연결하겠습니다.

먼저 로컬 애플리케이션이 사용할 IAM 사용자를 만듭니다. 이 사용자는 앞에서 만든 관리자 사용자와 다르며, **지정한 S3 버킷에만 접근하도록 권한을 줍니다.**

**IAM > 사용자 > 사용자 생성**에서 이름을 정합니다. 이번에는 사람이 콘솔에 로그인할 사용자가 아니므로 **AWS Management Console에 대한 사용자 액세스 권한 제공**은 활성화하지 않습니다.

권한 설정의 **직접 정책 연결 > 정책 생성**을 눌러줍니다. 이번에는 AWS의 기존 정책 대신 직접 만든 버킷에 대한 접근 정책을 작성합니다. 아래 JSON의 `{아까 만든 버킷이름}`을 중괄호까지 포함하여 실제 버킷 이름으로 바꿔줍니다.

![직접 정책 연결에서 S3 접근 정책 생성]({{ '/assets/img/1111/%E1%84%89%E1%85%B3%E1%84%8F%E1%85%B3%E1%84%85%E1%85%B5%E1%86%AB%E1%84%89%E1%85%A3%E1%86%BA%202026-11-11%20%E1%84%8B%E1%85%A9%E1%84%92%E1%85%AE%204.33.48.png' | relative_url }})
_직접 정책 연결에서 S3 접근 정책 생성_

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BookstoreBucketObjects",
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject",
        "s3:DeleteObject"
      ],
      "Resource": "arn:aws:s3:::{아까 만든 버킷이름}/*"
    },
    {
      "Sid": "BookstoreBucketList",
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket"
      ],
      "Resource": "arn:aws:s3:::{아까 만든 버킷이름}"
    }
  ]
}
```

정책 이름은 뒤에서 찾기 쉽도록 `aws-bucket-access`로 저장합니다. 사용자 생성 화면으로 돌아와 정책 목록을 새로고침한 뒤, 방금 만든 정책을 검색해 선택하고 사용자 생성을 마무리합니다.

위 정책에서 `버킷이름/*`은 버킷 안의 객체를 대상으로 하고, `버킷이름`은 버킷 자체를 대상으로 합니다. 파일 업로드·조회·삭제 권한과 버킷 목록 조회 권한을 나눈 이유입니다.

사용자 생성이 완료되었다면 **사용자 > 보안 자격 증명 > 액세스 키 만들기**로 들어갑니다. 용도는 **AWS 외부에서 실행되는 애플리케이션**으로 선택하고, 생성된 액세스 키와 비밀 액세스 키를 따로 보관합니다.

이 키는 잠시 뒤 로컬 애플리케이션에 전달합니다. 소스 코드에 직접 적거나 GitHub에 올리지 않습니다.

### SDK 의존성과 애플리케이션 설정

이제 우리가 만든 앱에서 SDK를 통해 S3에 접속할 차례입니다.

먼저 `build.gradle`의 `dependencies`에 다음 두 의존성을 추가합니다.

```groovy
dependencies {
    implementation platform('software.amazon.awssdk:bom:2.57.8')
    implementation 'software.amazon.awssdk:s3'
}
```

이어서 `application.yaml`에 아래 설정을 추가합니다.

기존에 `spring:` 블록이 있다면 새로 하나 더 만들지 않고 그 아래에 `servlet` 설정을 합쳐줍니다.

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 10MB
      max-request-size: 10MB
app:
  s3:
    bucket: ${S3_BUCKET:CHANGE-ME-본인-버킷-이름}
    region: ${AWS_REGION:ap-northeast-2}
```

이제 3개의 코드를 작성할 차례입니다. 각 클래스는 `@SpringBootApplication`이 있는 패키지의 하위에 두고, 본인 프로젝트에 맞는 `package` 선언을 추가합니다.

1. `S3Config`: S3 클라이언트와 미리 서명된 URL 생성기를 스프링 빈으로 등록
2. `S3StorageService`: 파일 업로드와 조회 URL 생성
3. `FileController`: 업로드·조회 API 제공

### S3 클라이언트 빈 등록 — S3Config

여기서는 접속할 리전만 지정합니다. 액세스 키를 코드에 넣지 않아도 AWS SDK가 실행 환경에서 자격 증명을 찾습니다. 로컬에서는 뒤에서 전달할 환경변수를 사용하고, ECS에서는 태스크 역할을 사용하도록 구성합니다. [AWS SDK 자격 증명 탐색 순서](https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/credentials-chain.html)를 참고하시면 됩니다.

```java
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import software.amazon.awssdk.regions.Region;
import software.amazon.awssdk.services.s3.S3Client;
import software.amazon.awssdk.services.s3.presigner.S3Presigner;

@Configuration
public class S3Config {

    @Value("${app.s3.region}")
    private String region;

    @Bean
    public S3Client s3Client() {
        return S3Client.builder()
                .region(Region.of(region))
                .build();   // 자격 증명은 체인이 알아서 찾습니다
    }

    @Bean
    public S3Presigner s3Presigner() {  // 조회 URL 생성에 사용
        return S3Presigner.builder()
                .region(Region.of(region))
                .build();
    }
}
```

### 파일 업로드와 조회 URL 생성 — S3StorageService

파일 이름이 겹치지 않도록 UUID를 붙여 객체 키를 만듭니다. 업로드 후에는 이 키를 반환하고, 조회할 때는 키를 사용하여 5분 동안 유효한 URL을 발급합니다.

```java
import java.io.IOException;
import java.time.LocalDate;
import java.util.UUID;
import lombok.RequiredArgsConstructor;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;
import org.springframework.web.multipart.MultipartFile;
import software.amazon.awssdk.core.sync.RequestBody;
import software.amazon.awssdk.services.s3.S3Client;
import software.amazon.awssdk.services.s3.model.PutObjectRequest;
import java.time.Duration;
import software.amazon.awssdk.services.s3.model.GetObjectRequest;
import software.amazon.awssdk.services.s3.presigner.model.GetObjectPresignRequest;
import software.amazon.awssdk.services.s3.presigner.S3Presigner;

@Service
@RequiredArgsConstructor
public class S3StorageService {

    private final S3Client s3Client;
    private final S3Presigner s3Presigner;

    @Value("${app.s3.bucket}")
    private String bucket;

    /** 파일을 S3에 올리고, 저장된 키를 돌려준다 */
    public String upload(MultipartFile file) {
        String key = createKey(file.getOriginalFilename());

        PutObjectRequest request = PutObjectRequest.builder()
                .bucket(bucket)
                .key(key)
                .contentType(file.getContentType())
                .build();

        try {
            s3Client.putObject(request,
                    RequestBody.fromInputStream(file.getInputStream(), file.getSize()));
        } catch (IOException e) {
            throw new IllegalStateException("S3 업로드 실패: " + key, e);
        }
        return key;
    }

    /** key에 대한 5분짜리 조회 링크를 발급한다 */
    public String createViewUrl(String key) {
        GetObjectRequest getRequest = GetObjectRequest.builder()
                .bucket(bucket)
                .key(key)
                .build();

        GetObjectPresignRequest presignRequest = GetObjectPresignRequest.builder()
                .getObjectRequest(getRequest)
                .signatureDuration(Duration.ofMinutes(5))
                .build();

        return s3Presigner.presignGetObject(presignRequest).url().toString();
    }

    /** covers/2026/11/550e8400-....png 형태의 키 생성 */
    private String createKey(String originalFilename) {
        String ext = "";
        if (originalFilename != null && originalFilename.contains(".")) {
            ext = originalFilename.substring(originalFilename.lastIndexOf('.'));
        }
        LocalDate today = LocalDate.now();
        return "covers/%d/%02d/%s%s".formatted(
                today.getYear(), today.getMonthValue(), UUID.randomUUID(), ext);
    }
}
```

### 업로드·조회 API — FileController

`POST /files`는 파일을 업로드하고, `GET /files/url`은 조회 URL을 반환합니다. 브라우저에서 이미지를 바로 확인하려면 `GET /files/view`를 사용합니다.

```java
import java.util.Map;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.multipart.MultipartFile;
import java.net.URI;
import org.springframework.web.bind.annotation.GetMapping;

@RestController
@RequestMapping("/files")
@RequiredArgsConstructor
public class FileController {

    private final S3StorageService s3StorageService;

    @PostMapping
    public ResponseEntity<Map<String, String>> upload(@RequestParam("file") MultipartFile file) {
        String key = s3StorageService.upload(file);
        return ResponseEntity.status(HttpStatus.CREATED).body(Map.of("key", key));
    }

    /** 조회 링크 발급 — 프론트엔드가 img src에 넣을 때 */
    @GetMapping("/url")
    public ResponseEntity<Map<String, String>> viewUrl(@RequestParam("key") String key) {
        return ResponseEntity.ok(Map.of("url", s3StorageService.createViewUrl(key)));
    }

    /** 즉시 열기 — 브라우저 주소창에서 바로 확인할 때 */
    @GetMapping("/view")
    public ResponseEntity<Void> view(@RequestParam("key") String key) {
        URI signedUrl = URI.create(s3StorageService.createViewUrl(key));
        return ResponseEntity.status(302).location(signedUrl).build();
    }
}
```

### 환경변수 등록

이어서 Compose 파일과 같은 폴더의 `.env` 파일에 아까 발급받은 S3용 사용자의 키와 버킷 이름을 등록합니다. 아래 값은 예시이므로 발급받은 값으로 바꿔줍니다.

```dotenv
AWS_ACCESS_KEY_ID=AKIA...(발급받은 값)
AWS_SECRET_ACCESS_KEY=...(발급받은 값)
AWS_REGION=ap-northeast-2
S3_BUCKET=본인 버킷명
```

`.env` 파일을 만드는 것과 애플리케이션에 환경변수를 전달하는 것은 별개입니다. Docker Compose를 사용 중이라면 기존 `app` 서비스의 `environment`에 아래 항목을 합쳐줍니다. 서비스 이름이 다르면 본인의 이름에 맞게 변경합니다.

```yaml
services:
  app:
    environment:
      AWS_ACCESS_KEY_ID: ${AWS_ACCESS_KEY_ID}
      AWS_SECRET_ACCESS_KEY: ${AWS_SECRET_ACCESS_KEY}
      AWS_REGION: ${AWS_REGION}
      S3_BUCKET: ${S3_BUCKET}
```

IntelliJ에서 직접 실행한다면 실행 구성의 **환경변수**에 같은 네 값을 넣습니다. 기본 Spring Boot 설정에서는 `.env` 파일을 만들었다고 자동으로 읽어오는 것은 아닙니다.

그리고 `.gitignore`에 `.env`를 추가합니다. Docker 이미지에도 들어가지 않도록 `.dockerignore`에도 `.env`를 추가해줍니다. 이미 Git에 올라간 키가 있다면 파일만 지우는 것으로 끝내지 않고 해당 키를 비활성화한 뒤 다시 발급해야 합니다.

### 업로드 결과 확인

이제 프로젝트를 실행한 뒤 Postman에서 아래처럼 요청합니다. Compose로 실행하는 경우에는 호스트의 8080 포트가 앱 컨테이너의 8080 포트에 연결되어 있어야 합니다.

1. 메서드를 `POST`, 주소를 `http://localhost:8080/files`로 설정합니다.
2. **Body > form-data**에서 이름을 `file`로 입력합니다.
3. 해당 항목의 타입을 **Text가 아닌 File**로 바꾸고 이미지 파일을 선택합니다.
4. 요청을 보내서 `201 Created`와 `key`가 반환되는지 확인합니다.

응답은 아래와 같은 형태입니다. UUID와 날짜는 업로드할 때마다 달라집니다.

```json
{
  "key": "covers/2026/11/생성된-UUID.png"
}
```

S3 버킷에도 같은 키로 파일이 올라왔는지 확인합니다. 이어서 Postman에서 `GET http://localhost:8080/files/url`을 요청하고, **Params**에 `key`와 방금 반환된 값을 넣습니다. 응답의 `url`을 브라우저에 붙여넣었을 때 이미지가 나오면 업로드와 조회까지 확인한 것입니다.

프로젝트에 Spring Security가 적용되어 있다면 해당 API의 인증 설정도 확인해야 합니다. `401`이나 `403` 응답이 나오면 애플리케이션 인증 문제인지, 로그에 기록된 S3 접근 권한 문제인지 먼저 구분합니다.

### 보안 그룹과 애플리케이션 연결

이렇게 생성한 RDS에 접근하기 위해서는 보안 그룹을 통해 인바운드 규칙을 지켜야 들어갈수 있습니다.

생성된 db페이지 안에 엔드포인트를 누르면 엔드포인트 주소가 나오고 생성시 추가한 보안 그룹도 확인이 가능합니다.

![생성한 RDS의 엔드포인트와 VPC 보안 그룹 확인]({{ '/assets/img/1111/%E1%84%89%E1%85%B3%E1%84%8F%E1%85%B3%E1%84%85%E1%85%B5%E1%86%AB%E1%84%89%E1%85%A3%E1%86%BA%202026-11-11%20%E1%84%8B%E1%85%A9%E1%84%92%E1%85%AE%206.11.35.png' | relative_url }})
_생성한 RDS의 엔드포인트와 VPC 보안 그룹 확인_

RDS 상태가 **사용 가능(Available)**으로 바뀌면 보안 그룹의 인바운드 규칙을 확인합니다. 로컬에서 연결하려면 **PostgreSQL / TCP 5432 / 소스 내 IP** 규칙이 필요합니다. 이미 내 PC의 공인 IP가 등록되어 있다면 그대로 사용하고, 없다면 추가합니다.

이제 기존 로컬 DB 연결 정보를 RDS 정보로 바꿉니다. 아래는 `application.yaml`에서 환경변수로 연결 정보를 받도록 구성하는 예시입니다. 기존 `spring:` 설정에 합쳐줍니다.

```yaml
spring:
  datasource:
    url: ${SPRING_DATASOURCE_URL}
    username: ${SPRING_DATASOURCE_USERNAME}
    password: ${SPRING_DATASOURCE_PASSWORD}
  jpa:
    hibernate:
      ddl-auto: ${SPRING_JPA_HIBERNATE_DDL_AUTO:update}
```

예를 들어 로컬에서 `jdbc:postgresql://localhost:5433/db_project`로 연결했다면, RDS에서는 아래와 같이 변경합니다. Docker의 호스트 포트인 5433 대신 **RDS에 표시된 포트인 5432**를 사용합니다.

```dotenv
SPRING_DATASOURCE_URL=jdbc:postgresql://본인의-RDS-엔드포인트:5432/db_project
SPRING_DATASOURCE_USERNAME=postgres
SPRING_DATASOURCE_PASSWORD=본인의-마스터-암호
SPRING_JPA_HIBERNATE_DDL_AUTO=update
```

마스터 사용자 이름을 `postgres`가 아닌 다른 이름으로 만들었다면 그 값도 변경합니다. `ddl-auto=update`는 이번 실습용 설정이며, 기존에 `create`로 설정되어 있다면 시작할 때 테이블을 다시 만들 수 있으니 확인합니다.

Compose로 실행한다면 `.env`에 위 네 값을 추가하고, 기존 `app.environment`에도 아래 항목을 합쳐줍니다. 앞에서 추가한 S3 설정도 유지합니다.

```yaml
services:
  app:
    environment:
      SPRING_DATASOURCE_URL: ${SPRING_DATASOURCE_URL}
      SPRING_DATASOURCE_USERNAME: ${SPRING_DATASOURCE_USERNAME}
      SPRING_DATASOURCE_PASSWORD: ${SPRING_DATASOURCE_PASSWORD}
      SPRING_JPA_HIBERNATE_DDL_AUTO: ${SPRING_JPA_HIBERNATE_DDL_AUTO}
```

RDS를 사용한다고 로컬 DB의 `volume`을 바꿀 필요는 없습니다. 로컬 DB 서비스에 대한 `depends_on`이 남아 있다면 RDS 연결에 맞게 제거하고, 로컬 DB 데이터와 볼륨은 그대로 둡니다. 기존 데이터가 RDS로 자동 복사되는 것은 아니므로 데이터 이전이 필요하면 별도로 진행해야 합니다.

Compose 서비스 이름이 `app`이고 `build`가 설정되어 있다면 아래처럼 앱을 다시 생성하여 환경변수와 변경된 코드를 반영합니다. IntelliJ로 실행한다면 실행 구성의 환경변수를 바꾼 뒤 앱을 다시 실행합니다.

```bash
docker compose up -d --build app
docker compose logs -f app
```

앱을 다시 실행한 뒤, DB를 사용하는 기존 API로 데이터를 저장하고 조회해봅니다. 앱 시작만 확인하는 것보다 실제 저장·조회까지 성공하는지 확인하는 것이 좋습니다.

- 연결 시간이 초과된다면 RDS 상태, 엔드포인트, 포트, 퍼블릭 액세스와 내 IP 인바운드 규칙을 확인합니다.
- 인증 오류가 나면 마스터 사용자 이름과 암호를 확인합니다.
- 데이터베이스가 없다는 오류가 나면 JDBC URL 마지막 이름과 초기 데이터베이스 이름이 같은지 확인합니다.

## 5. ECR과 ECS로 애플리케이션 배포

이제 파일은 S3에, DB는 RDS에 연결했습니다. 다음은 로컬에서 실행하던 애플리케이션까지 AWS에 올리는 과정입니다. 이 부분이 가장 많은 작업이 필요합니다.

먼저 Docker 이미지를 ECR에 보관하고, ECS에서 그 이미지를 가져와 실행합니다. ECS는 태스크 정의, 태스크, 서비스, 클러스터로 구성됩니다.

| 구성 요소 | 역할 |
| --- | --- |
| 태스크 정의 | 어떤 이미지를 어떤 환경변수로 실행할지 정의 |
| 태스크 | 태스크 정의로 실행한 컨테이너들 |
| 서비스 | 실행할 태스크 수를 유지하고, 종료된 태스크를 다시 실행 |
| 클러스터 | 태스크와 서비스를 관리하는 공간 |

### Docker 이미지 빌드 준비

ECR에는 소스 코드가 아닌 Docker 이미지를 올립니다. 프로젝트 최상위에 `Dockerfile`이 있고, 로컬에서 앱 이미지를 빌드할 수 있어야 합니다.

이미 사용 중인 Dockerfile이 있다면 그대로 확인합니다. 아직 없다면 아래는 **Java 17과 Gradle을 사용하는 Spring Boot 프로젝트용 예시**입니다. Java 21 프로젝트라면 두 이미지의 버전도 21로 맞춰줍니다.

```dockerfile
FROM eclipse-temurin:17-jdk AS build
WORKDIR /workspace
COPY . .
RUN chmod +x gradlew \
    && ./gradlew --no-daemon bootJar \
    && find build/libs -maxdepth 1 -name '*.jar' ! -name '*-plain.jar' \
       -exec cp {} /workspace/app.jar \;

FROM eclipse-temurin:17-jre
WORKDIR /app
COPY --from=build /workspace/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

이 예시는 컨테이너 안에서 `bootJar`까지 실행합니다. 기존 Dockerfile이 `build/libs/*.jar`를 복사하는 방식이라면 `docker build` 전에 `./gradlew bootJar`를 실행해야 합니다. 뒤의 GitHub Actions에서도 같은 준비가 필요합니다.

위처럼 컨테이너 안에서 JAR를 빌드한다면 `.dockerignore`에 아래 항목을 추가합니다. `.gradle`과 프로젝트의 `gradle` 폴더는 다르므로 Gradle Wrapper가 있는 `gradle` 폴더는 제외하지 않습니다.

```text
.git
.gradle
build
.env
.env.*
```

기존 Dockerfile이 **로컬의 `build/libs`에서 JAR를 복사하는 방식이라면 `build`는 `.dockerignore`에서 제외하지 않습니다.** 복사할 JAR까지 빌드 대상에서 빠지기 때문입니다. 멀티 모듈 프로젝트라면 JAR 경로와 빌드 명령은 실행할 모듈에 맞게 수정합니다.

### ECR 리포지토리 생성과 이미지 업로드

먼저 이미지를 ECR에 올립니다. ECR은 Docker Hub처럼 이미지를 올리는 AWS 버전입니다.

먼저 AWS에서 ECR로 들어가 리포지토리를 생성합니다. 프라이빗 리포지토리에서 이름을 정하고 생성합니다. 이 글의 로그인과 이미지 주소는 프라이빗 ECR 기준입니다.

생성된 리포지토리의 URI를 복사해둡니다. 여기서 레지스트리 주소와 리포지토리 URI가 조금 다르므로 구분해야 합니다.

| 구분 | 예시 |
| --- | --- |
| 레지스트리 주소 | `123456789012.dkr.ecr.ap-northeast-2.amazonaws.com` |
| 리포지토리 URI | `123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/aws-study` |
| 태그까지 포함한 이미지 주소 | `123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/aws-study:latest` |

#### 로컬 CLI 인증

콘솔에 로그인했다고 터미널의 AWS CLI도 로그인된 것은 아닙니다. 또 앞에서 만든 S3 전용 사용자는 ECR 업로드 권한이 없으므로 그대로 사용하면 권한 오류가 납니다.

처음 설정한다면 IAM에서 로컬 ECR 업로드용 사용자를 별도로 만들고, 콘솔 접근은 끈 상태에서 `AmazonEC2ContainerRegistryPowerUser` 정책을 연결합니다. 해당 사용자의 액세스 키를 CLI 용도로 발급받은 뒤 아래 프로필에 등록합니다. 이미 ECR 업로드 권한이 있는 CLI 프로필이 있다면 그 프로필을 사용하셔도 됩니다.

```bash
aws configure --profile aws-deploy
```

차례대로 업로드용 사용자의 액세스 키, 비밀 액세스 키, 기본 리전 `ap-northeast-2`, 출력 형식 `json`을 입력합니다. 키는 명령어에 직접 적지 않고 입력 프롬프트에 넣습니다. 프로필 설정 방식은 [AWS CLI 공식 문서](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-files.html)를 참고하시면 됩니다.

```bash
aws sts get-caller-identity --profile aws-deploy
```

응답의 `Account`와 `Arn`이 이번 실습 계정과 업로드용 사용자인지 확인합니다. 다른 계정이 나온다면 프로필이나 터미널에 이미 설정된 AWS 환경변수를 먼저 확인합니다.

#### 로그인과 이미지 push

아래 값에서 계정 ID와 리포지토리 이름을 본인의 것으로 바꿔줍니다. 이후 명령은 같은 터미널에서 이어서 실행합니다.

```bash
AWS_ACCOUNT_ID="본인의-12자리-계정-ID"
ECR_REPOSITORY="aws-study"
ECR_REGISTRY="${AWS_ACCOUNT_ID}.dkr.ecr.ap-northeast-2.amazonaws.com"

aws ecr get-login-password --region ap-northeast-2 --profile aws-deploy \
  | docker login --username AWS --password-stdin "$ECR_REGISTRY"
```

`Login Succeeded`가 나오면 이미지를 빌드한 뒤 태그를 붙이고 push합니다. 아래 이미지는 ECS에서 사용할 Linux/X86_64 환경에 맞춰 `linux/amd64`로 빌드합니다.

```bash
docker build --platform linux/amd64 -t aws-study .
docker tag aws-study:latest "$ECR_REGISTRY/$ECR_REPOSITORY:latest"
docker push "$ECR_REGISTRY/$ECR_REPOSITORY:latest"
```

리포지토리의 **푸시 명령 보기**에서도 본인 주소가 들어간 명령을 확인할 수 있습니다. 명령의 기본 흐름은 [ECR 이미지 업로드 문서](https://docs.aws.amazon.com/AmazonECR/latest/userguide/docker-push-ecr-image.html)와 같습니다.

이미지 업로드 후 ECR에서 결과를 확인합니다. 이번 실습에서는 아래처럼 3개 항목이 표시되었습니다.

### 애플리케이션과 RDS 보안 그룹 연결

이렇게 태스크 정의까지 만들었다면 이제 접속을 위해 총 2가지 접속이 필요합니다.

1. 외부 → 애플리케이션 태스크의 **8080 포트**
2. 애플리케이션 태스크 → RDS의 **5432 포트**

먼저 앱(8080)으로 가는 보안 그룹을 만들어야 합니다.

EC2 > 보안 그룹 > 보안 그룹 생성
이름과 설명을 추가한 뒤 인바운드는 **사용자 지정 TCP / 포트 8080 / 소스 내 IP**로 설정합니다. 이번 실습은 외부에 공개할 목적이 아니므로 내 PC의 공인 IP만 허용했습니다.

### 배포 상태와 접속 확인

생성 후 서비스에서 태스크가 **RUNNING** 상태가 되는지 확인합니다. 곧바로 종료된다면 서비스의 이벤트, 중지된 태스크의 중지 사유, 컨테이너 로그 순서로 확인합니다. 앱이 시작되기 전에 실패한 경우에는 애플리케이션 로그가 없을 수도 있습니다.

대표적으로 환경변수가 누락되거나 RDS 연결이 안 되어 앱이 종료될 수 있습니다. 이미지를 가져오지 못했다는 오류라면 이미지 주소, 태스크 실행 역할, 서브넷의 외부 통신 경로도 확인합니다.

태스크가 실행되었다면 **클러스터 > 서비스 > 태스크 > 구성**에서 퍼블릭 IP를 확인합니다. Postman의 주소를 `http://퍼블릭-IP:8080/files`로 바꾸고, 앞에서 했던 파일 업로드와 조회를 다시 요청합니다. DB를 사용하는 API도 함께 확인합니다.

![실행 중인 태스크에서 접속에 사용할 퍼블릭 IP 확인]({{ '/assets/img/1111/%E1%84%89%E1%85%B3%E1%84%8F%E1%85%B3%E1%84%85%E1%85%B5%E1%86%AB%E1%84%89%E1%85%A3%E1%86%BA%202026-11-11%20%E1%84%8B%E1%85%A9%E1%84%92%E1%85%AE%2010.16.11.png' | relative_url }})
_실행 중인 태스크에서 접속에 사용할 퍼블릭 IP 확인_

접속이 안 되면 먼저 앱 보안 그룹의 8080 규칙에 현재 내 공인 IP가 들어 있는지 확인합니다. 앱은 실행되지만 DB 요청만 실패한다면 RDS의 5432 규칙과 앱 환경변수를 확인합니다.

집이나 사무실의 네트워크가 바뀌면 내 공인 IP도 달라질 수 있습니다. 또 태스크를 다시 배포하면 퍼블릭 IP가 바뀔 수 있으므로 접속 주소도 다시 확인해야 합니다.

## 6. GitHub Actions로 CI/CD 구성

마지막으로 CI/CD 자동 배포입니다.

지금까지는 배포할 때마다 이미지를 만들고 ECR에 업로드한 뒤, 새 이미지를 사용하도록 태스크 정의와 서비스를 갱신해야 했습니다. 이제 GitHub의 `main` 브랜치에 push가 발생하면 이 과정을 자동으로 실행하도록 만들어보겠습니다. PR을 `main`에 merge한 경우에도 `main`에 변경이 반영되면서 실행됩니다.

먼저 수동으로 배포한 서비스가 정상 실행되는 상태에서 진행합니다. 자동 배포도 같은 서비스와 태스크 정의를 사용하기 때문입니다.

프로젝트에 `.github/workflows/deploy.yml` 파일을 만듭니다. GitHub Actions가 AWS를 수정하려면 인증이 필요한데, 여기서는 액세스 키를 GitHub에 저장하는 대신 **OIDC로 배포 역할을 맡는 방식**을 사용합니다.

### GitHub OIDC 공급자 등록

먼저 AWS에 IAM > ID 제공업체 > 공급자 추가에 아래 값을 추가 후 생성합니다.

- **공급자 URL:** `https://token.actions.githubusercontent.com`
- **대상(Audience):** `sts.amazonaws.com`

![GitHub Actions용 OpenID Connect 공급자 추가]({{ '/assets/img/1111/%E1%84%89%E1%85%B3%E1%84%8F%E1%85%B3%E1%84%85%E1%85%B5%E1%86%AB%E1%84%89%E1%85%A3%E1%86%BA%202026-11-11%20%E1%84%8B%E1%85%A9%E1%84%92%E1%85%AE%2010.29.00.png' | relative_url }})
_GitHub Actions용 OpenID Connect 공급자 추가_

### GitHub Actions 배포 역할 생성

다음은 역할 만들기입니다.

IAM > 역할 > 역할 생성
신뢰할 수 있는 엔터티 유형을 웹 자격 증명을 선택 후 아래처럼 값을 넣습니다.

- **자격 증명 공급자:** `token.actions.githubusercontent.com`
- **Audience:** `sts.amazonaws.com`
- **GitHub 조직/사용자명:** 본인 GitHub 아이디
- **GitHub 리포지토리:** `db_project`

![웹 자격 증명으로 GitHub Actions 배포 역할 생성]({{ '/assets/img/1111/%E1%84%89%E1%85%B3%E1%84%8F%E1%85%B3%E1%84%85%E1%85%B5%E1%86%AB%E1%84%89%E1%85%A3%E1%86%BA%202026-11-11%20%E1%84%8B%E1%85%A9%E1%84%92%E1%85%AE%2010.53.40.png' | relative_url }})
_웹 자격 증명으로 GitHub Actions 배포 역할 생성_

권한은 2가지를 등록합니다.

- `AmazonEC2ContainerRegistryPowerUser`: ECR push용
- `AmazonECS_FullAccess`: ECS 배포용

역할 이름은 github-actions-aws로 역할을 생성하였습니다.

이렇게 만든 역할에 들어가 신뢰 관계를 아래처럼 수정합니다.

`본인계정ID`, `본인아이디`, `본인리포지토리`를 실제 값으로 바꿔줍니다. 아래 조건은 해당 리포지토리의 `main` 브랜치에서 실행되는 작업만 이 역할을 맡도록 제한한 예제입니다. 다른 배포 브랜치를 쓰면 이 조건과 워크플로의 브랜치를 함께 변경합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::본인계정ID:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          "token.actions.githubusercontent.com:sub": "repo:본인아이디/본인리포지토리:ref:refs/heads/main"
        }
      }
    }
  ]
}
```

### 태스크 역할을 전달하는 권한 설정

다음 작업은 배포 역할이 태스크 역할을 전달할 수 있도록 권한을 설정하는 것입니다. 앞에서 만든 **github-actions-aws** 역할에 `iam:PassRole` 권한을 추가합니다.

해당 역할에 권한 추가에 인라인 정책 생성을 한 뒤 JSON으로 아래 값을 추가한 뒤 이름을 pass-task-roles로 저장합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": [
        "arn:aws:iam::본인계정ID:role/aws-study-task-role",
        "arn:aws:iam::본인계정ID:role/ecsTaskExecutionRole"
      ]
    }
  ]
}
```

저장 후 **github-actions-aws의 ARN**을 복사해둡니다. 아래 워크플로의 `role-to-assume`에 사용합니다.

`Resource`에 넣은 두 역할 ARN도 실제 태스크 정의의 태스크 역할과 실행 역할 ARN으로 맞춰줍니다. 이 권한은 앱에 추가하는 것이 아니라 **GitHub Actions 배포 역할에 추가하는 권한**입니다.

### 배포 워크플로 작성

아까 프로젝트에 만든 `deploy.yml`에 아래 코드를 넣습니다. 각 값은 AWS에서 아래 위치를 확인하여 바꿔줍니다.

| 워크플로 항목 | 넣을 값 |
| --- | --- |
| `ECR_REPOSITORY` | ECR 리포지토리 이름만 입력. 레지스트리 주소는 제외 |
| `ECS_CLUSTER` | ECS 클러스터 이름 |
| `ECS_SERVICE` | 해당 클러스터 안의 서비스 이름 |
| `TASK_FAMILY` | 태스크 정의의 패밀리 이름 |
| `role-to-assume` | `github-actions-aws` 역할의 ARN |
| `container-name` | 태스크 정의 안의 컨테이너 이름 |

이 워크플로는 앞에서 소개한 것처럼 Dockerfile 내부에서 JAR까지 빌드하는 구성을 기준으로 합니다. Dockerfile이 미리 빌드한 JAR를 복사하는 방식이라면 이미지 빌드 단계 전에 프로젝트에 맞는 JDK 설정과 `./gradlew bootJar` 실행 단계를 추가해야 합니다.

{% raw %}

```yaml
name: deploy

on:
  push:
    branches: [main]

permissions:
  id-token: write     # OIDC 토큰 발급 허용
  contents: read

env:
  AWS_REGION: ap-northeast-2
  ECR_REPOSITORY: "본인-ECR-리포지토리-이름"
  ECS_CLUSTER: "본인-ECS-클러스터-이름"
  ECS_SERVICE: "본인-ECS-서비스-이름"
  TASK_FAMILY: "본인-태스크-정의-패밀리"

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: 코드 받기
        uses: actions/checkout@v4

      - name: AWS 인증 (OIDC — 키 없음)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: "arn:aws:iam::본인계정ID:role/github-actions-aws"
          aws-region: ${{ env.AWS_REGION }}

      - name: ECR 로그인
        id: ecr-login
        uses: aws-actions/amazon-ecr-login@v2

      - name: 이미지 빌드하고 push (태그 = 커밋 해시)
        id: build-image
        env:
          REGISTRY: ${{ steps.ecr-login.outputs.registry }}
          IMAGE_TAG: ${{ github.sha }}
        run: |
          docker build -t $REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG .
          docker push $REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG
          echo "image=$REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG" >> $GITHUB_OUTPUT

      - name: 현재 태스크 정의 내려받기
        run: |
          aws ecs describe-task-definition --task-definition $TASK_FAMILY \
            --query taskDefinition > task-definition.json

      - name: 태스크 정의에 새 이미지 끼우기
        id: render
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with:
          task-definition: task-definition.json
          container-name: "본인-컨테이너-이름"
          image: ${{ steps.build-image.outputs.image }}

      - name: ECS에 배포하고 안정화까지 대기
        uses: aws-actions/amazon-ecs-deploy-task-definition@v2
        with:
          task-definition: ${{ steps.render.outputs.task-definition }}
          cluster: ${{ env.ECS_CLUSTER }}
          service: ${{ env.ECS_SERVICE }}
          wait-for-service-stability: true
```

{% endraw %}

### 자동 배포 확인

위 코드의 `본인-...` 값과 계정 ID를 실제 AWS 설정에 맞게 수정한 뒤, 해당 프로젝트의 `main` 브랜치에 push합니다.

GitHub 리포지토리의 **Actions > deploy**에서 실행된 작업을 열어봅니다. 인증, ECR 로그인, 이미지 빌드와 push, 태스크 정의 변경, ECS 배포 순서로 진행됩니다.

실패했다면 빨간색으로 표시된 단계의 로그를 먼저 확인합니다.

| 실패한 단계 | 먼저 확인할 것 |
| --- | --- |
| AWS 인증 | 배포 역할 ARN, OIDC 공급자, 신뢰 관계의 리포지토리와 브랜치 |
| 이미지 빌드 | Dockerfile 경로, JDK 버전, JAR 빌드 방식 |
| ECR push | 리포지토리 이름과 리전, 배포 역할의 ECR 권한 |
| 태스크 정의 변경 | 패밀리 이름과 컨테이너 이름 |
| ECS 배포·안정화 대기 | `iam:PassRole`, 서비스 이벤트, 태스크 중지 사유와 앱 로그 |

전체 단계가 성공했다면 ECR에 해당 커밋 해시를 태그로 가진 이미지가 올라왔는지, ECS 서비스가 새 태스크 정의를 사용하는지 확인합니다. 마지막으로 새 태스크의 퍼블릭 IP를 확인하고 Postman에서 변경된 API 동작을 확인해줍니다.

여기까지 되면 코드를 수정해서 `main`에 반영할 때 이미지 업로드부터 서비스 배포까지 자동으로 이어집니다. 이번 글은 배포 자동화까지 연결하는 실습이며, 별도의 테스트 검증 단계는 이 워크플로에 포함하지 않았습니다.

## 7. 실습을 마친 뒤 리소스 정리

실습을 끝냈다면 사용하지 않을 리소스도 정리해줍니다. 브라우저나 로컬 Docker를 종료하는 것만으로 AWS 리소스가 종료되는 것은 아닙니다. 아래는 **이번 실습에서 만든 리소스를 더 사용하지 않을 때** 확인할 순서입니다.

1. **GitHub Actions**: 배포 워크플로를 비활성화하거나 제거하여 실수로 다시 배포하지 않도록 합니다.
2. **ECS**: 서비스의 원하는 태스크 수를 0으로 바꾸고, 실행 중인 태스크가 없는지 확인합니다. 이후 실습용 서비스와 클러스터를 삭제합니다. 별도로 실행한 태스크가 있다면 그것도 확인합니다.
3. **RDS**: 필요한 데이터가 있는지 먼저 확인한 뒤 실습 DB를 삭제합니다. 삭제 방지가 켜져 있으면 먼저 해제해야 합니다. 최종 스냅샷과 자동 백업을 남길지는 데이터 보관 필요에 따라 선택합니다.
4. **S3와 ECR**: 보관할 파일이나 이미지가 없다면 실습용 객체·이미지를 지운 뒤 버킷과 리포지토리를 정리합니다. S3 버전 관리를 켰다면 이전 버전도 확인합니다.
5. **CloudWatch Logs**: 이번 실습에서 생성한 로그 그룹의 보관 필요 여부를 확인합니다.
6. **IAM과 보안 그룹**: 더 이상 사용하지 않는 실습용 액세스 키를 비활성화·삭제하고, 다른 곳에서 사용하지 않는 역할·정책·보안 그룹을 정리합니다. 관리자 사용자나 기본 VPC까지 삭제하는 것은 아닙니다.

RDS 인스턴스를 삭제해도 보존한 스냅샷과 백업은 남을 수 있으며 비용이 발생할 수 있습니다. 데이터를 남길지 결정할 때 [RDS 삭제 안내](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_DeleteInstance.html)도 함께 확인합니다.

마지막으로 사용한 리전의 리소스 목록과 Billing 화면을 확인합니다. 비용 표시에는 반영 시간이 있으므로, 삭제 직후 금액만으로 모든 정리가 끝났다고 판단하지 않습니다.
